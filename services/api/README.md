# @byond/api — Core Platform API

The BYOND cloud control plane: tenants, users, auth + RBAC (Phase 2), stores/locations, platform modules, the append-only audit log, product catalog + inventory ledger (Phase 3), retail units, devices, and the edge-registration foundation (Phase 4), checkout sessions + orders (Phase 5), the provider-neutral payment abstraction + reconciliation foundation (Phase 6), CV product recognition + virtual basket (Phase 7), the CV inference adapter + event queue foundation (Phase 9), and the video ingestion + crop extraction MVP (Phase 10). NestJS 11 + TypeScript strict + Prisma + PostgreSQL.

### Phase 6 — payments & reconciliation (foundation only)

Phase 6 introduces a **provider-neutral** payment abstraction. It deliberately does **not** integrate a live payment gateway:

- **No live gateway / no provider SDK.** There is no MyFatoorah/Stripe/Tap/HyperPay/Moyasar (or any) SDK. `provider` is a generic enum (`SIMULATED`/`MANUAL`); real gateway adapters plug in through this abstraction later.
- **Authorization and capture are SIMULATED** through an explicit payment state machine (`CREATED → REQUIRES_AUTHORIZATION → AUTHORIZED → CAPTURE_PENDING → CAPTURED`, plus `FAILED`/`CANCELLED`/`VOIDED`/`EXPIRED`). Invalid transitions are rejected, terminal states are protected, and every mutation is audited.
- **No raw card data or secrets, ever.** Only opaque provider references and **safe** card metadata are stored — `instrumentBrand`, `instrumentLast4` (exactly four digits, DB-enforced), `instrumentExpiryMonth/Year`, `instrumentWallet`. Raw PAN, CVV, PIN, magnetic-track data, provider secret keys, bearer tokens, API keys, and raw webhook secrets/payloads are **never** accepted, stored, logged, or audited (screened by `common/sensitive-keys`).
- **Order is not "paid" unless the payment reaches CAPTURED.** A captured intent is the only path that flips a linked order's `paymentStatus` to `PAID`; a failure/void never marks an order paid, and a `PAID` order is never downgraded. Refunds are reserved (`REFUND_PENDING`/`REFUNDED`) but **not** implemented — no money movement.
- **Idempotency & duplicate-capture safety.** Create/authorize/capture carry tenant-scoped idempotency keys; a duplicate capture with the same key **never** moves money twice. Provider events are deduplicated per `(tenant, provider, providerEventId)`.
- **Provider events are an ingestion FOUNDATION** — authenticated/admin-only (`POST /payment-events/simulate`), **not** a public webhook. Only normalized fields are stored (no raw payload, no signature verification yet).
- **Reconciliation is a FOUNDATION** — a `PENDING` record is seeded on capture, with read models and a manual status update. No settlement accounting, provider import, or Zoho integration.

## Architecture notes

- **Tenant isolation** — every tenant-scoped repository extends [`TenantScopedRepository`](src/prisma/tenant-scoped.repository.ts): all methods take `tenantId` first and merge it into every query; a blank tenantId throws, never wildcards. Platform-scoped repositories (Tenant, Permission, PlatformModule) are explicitly documented as such.
- **Platform vs tenant users** — single `User` table with a `userType` discriminator; a DB CHECK constraint enforces `PLATFORM ⇔ tenantId IS NULL`.
- **Audit log** — append-only: no update/delete service methods, a DB trigger rejects `UPDATE`/`DELETE`, and before/after snapshots pass a redaction filter.
- **Catalogs as code** — permissions ([permission.catalog.ts](src/access-control/permission.catalog.ts)) and platform modules ([platform-module.catalog.ts](src/platform-modules/platform-module.catalog.ts)) are typed constants; the seed upserts from them, so codes never drift.
- **Auth** — Phase 2: bcrypt credentials, short-lived HS256 JWTs, a global auth guard, and a permissions guard that audits every denial. Tenant context comes exclusively from the authenticated user — a `tenantId` in any request body is rejected by the global whitelist `ValidationPipe`.
- **Stores / units / devices (Phase 4)** — the `Location` entity is the store/branch/site concept, served under both `/locations` and `/stores`. `RetailUnit` (smart fridge/shelf/kiosk/... with a DRAFT→ACTIVE→MAINTENANCE/DISABLED→RETIRED lifecycle) belongs to a store; `Device` (camera/lock/sensor/... with per-tenant-unique serials, heartbeats, and `lastSeenAt`) belongs to a unit. Composite same-tenant FKs in migration SQL make cross-tenant references impossible even if an unscoped id slipped through code. Deletion is Restrict-guarded: stores with units/inventory and units with devices return controlled 409s. **Reparenting is likewise guarded since Phase 10**: moving a unit to another store or a device to another unit is a controlled 409 while live (non-deleted) Phase 10 video assets reference it — assets denormalize the store/unit/device hierarchy they were captured under as historical evidence, and reparenting would strand their crops at the inference queue with a stale tuple (unit-location-mismatch / device-unit-mismatch). Delete the referencing assets first (their recorded bindings are the evidence of where the footage was captured); soft-deleted assets never block, and the check runs under the same unit/device advisory locks the upload path holds, so a concurrent upload cannot slip past it.
- **Edge registration (Phase 4)** — `POST /devices/:id/registration-token` (permission `device:register`) issues a one-time token whose **SHA-256 hash alone** is stored; the plaintext is returned once and never logged or audited. The unauthenticated `POST /edge/register` redeems it (serial-bound, single-use, 60-minute expiry; every failure is the same generic 401). Phase 7 will exchange this registration for long-lived edge credentials — none are minted today.
- **Checkout sessions + orders (Phase 5)** — tenant-scoped checkout sessions (`OPEN → ACTIVE → PENDING_REVIEW → COMPLETED/CANCELLED/EXPIRED`) belong to a store and retail unit, carry basket lines with immutable product snapshots (sku/name/UoM/quantity), and complete atomically into a `CONFIRMED` order in a single transaction: per-line `SALE` inventory movements (conditional decrement, `referenceType='Order'`) either all succeed or the whole completion — order included — rolls back. Order numbers are unique per tenant (`ORD-000001`); duplicate completion is prevented by tenant-scoped idempotency keys that replay the original result. **No payment capture exists in Phase 5** — pricing/totals columns are nullable placeholders and no order state means "paid"; payments arrive in a later phase.
- **Vendor-neutral evidence lineage (Phase 5, hardened in Phase 7)** — sessions, basket lines, and order lines carry generic evidence/source reference fields (`sourceType`, `sourceId`, `evidenceBundleId`, `visionEventId`, `vlmReviewId`, `evidenceScore`, `evidenceQuality`, `reasonCodes`). Since Phase 7, `evidenceBundleId`/`visionEventId` are **canonical** references to the Phase 7 `EvidenceBundle`/`VisionEvent` tables: validated tenant-scoped at the data-access layer and backstopped by composite same-tenant FKs, so dangling or cross-tenant CV lineage is impossible. Opaque values stored by the Phase 5 API before those tables existed are preserved verbatim in separate read-only `externalVisionEventRef`/`externalEvidenceBundleRef` columns by the `legacy_vision_ref_compat` migration — they are never resolved against (or promoted to) Phase 7 lineage, and completion copies them onto orders in those same external columns. **Basket-affecting** vision events can never be cited as NEW manual line lineage in any status (controlled 409): pending events would be double-counted when later approved, and decided events already carry their one-shot recorded effect — `POST /vision-events/:id/review` is the only path that applies them to a basket. A patched line may only keep the event reference it already carries (so review-created lines stay manually correctable).
- **CV product recognition + virtual basket (Phase 7)** — the core USP flow: camera/CV event → evidence bundle → SKU candidates → review/policy decision → virtual basket line. `POST /vision-events` (permission `vision:ingest`, module `cv`) ingests normalized product interaction events (`PRODUCT_PICKUP`, `PRODUCT_RETURN`, `PRODUCT_TRANSFER`, `CART_INSERTION`, `EXIT_RECONCILIATION`) with ranked SKU candidates (snapshotted from the tenant catalog), an optional device/session binding, and an optional **lineage-only evidence bundle** (Phase 7 accepts NO evidence payloads: no artifact descriptors, no metadata objects, no URIs/storage keys/hashes, no provenance strings, no inline media in any encoding — the bundle is a lightweight append-only lineage record of `sourceType` + capture window, published as a closed OpenAPI schema with `additionalProperties: false`; every removed payload field is a controlled 400, and external media references arrive in a future evidence storage phase). Ingestion never touches the basket or inventory; events land in `PENDING_REVIEW`. `POST /vision-events/:id/review` (permission `vision:review`) records exactly one terminal decision per event — APPROVE applies the top candidate, OVERRIDE applies the reviewer's product/quantity, REJECT records only — and the decision, the event status flip, the basket line add/increment (pickup, cart insertion) or decrement/soft-remove (return), and every audit row commit or roll back as **one transaction** under the same session/product advisory locks as checkout. `EvidenceBundle`, `VisionEventCandidate`, and `VisionEventReview` are append-only (DB triggers) — evidence and decisions are tamper-evident. Provider neutrality is structural: `sourceType` is a closed enum, reason codes are lowercase slugs, and the user-supplied provenance strings of earlier drafts (`sourceId`/`modelName`/`modelVersion`) are removed — those columns are server-controlled and always null in Phase 7. Remaining free strings (idempotency keys, candidate labels, review reasons) are screened against credential-/payment-bearing content before persistence. No camera integration, edge runtime, or training pipeline exists in this phase.

- **CV inference adapter & event queue (Phase 9)** — the provider-neutral seam between model output and the Phase 7 vision flow, following the event-driven CV architecture (continuous lightweight tracking on DOWNSCALED streams → trigger layer → heavy inference on high-resolution triggered crops only; a VLM only ever verifies cropped product patches). `POST /inference/jobs` (permission `inference:manage`, module `inference`) queues a provider-neutral `InferenceJob` (`TRACKING_EVENT`, `SHELF_AUDIT`, `PRODUCT_RECOGNITION`, `OCR_REVIEW`, `VLM_REVIEW`, `EXIT_RECONCILIATION`; `QUEUED → RUNNING → SUCCEEDED/FAILED`, `CANCELLED` reserved) with an optional store/unit/device/session binding, a 0–1000 priority, a tenant-scoped idempotency key (replays, never duplicates), and a **SAFE input descriptor**: crops/zones/frames are referenced BY ID only — raw media, media/storage URLs, signed URLs, artifact descriptors, inline base64, and credential-/payment-bearing content are all controlled 400s, screened by KEY and by VALUE (URI schemes, media file extensions, presigned-URL signature params). The job table IS the queue (deterministic claim ordering: priority DESC, requestedAt ASC, id ASC; race-safe compare-and-set transitions; lease-based claims — every claim takes a bounded lease and increments an attempt counter, and expired leases from crashed workers are reclaimed on the next claim pass: requeued while attempts remain, `LEASE_EXPIRED`-failed once the budget is spent, each reclaim audited as a system action; `POST /inference/jobs/reclaim-expired` (permission `inference:manage`) triggers the same sweep explicitly so an operator can recover a stranded job without waiting for an unrelated start, and `complete`/`fail` carry the caller-observed claim `attempt` so a stale worker's report is fenced out with a 409 after a reclaim) behind an `InferenceQueuePort` abstraction — message-broker adapters (Redis/NATS/MQTT/Kafka-style) can implement the same port later; none is a dependency today. Adapters implement a provider-neutral `InferenceAdapter` contract (`validateInput`/`run`/`normalizeResult`); Phase 9 registers exactly one, the **simulated** adapter — `POST /inference/jobs/:id/complete` (permission `inference:simulate`) takes sample model output — including the required SOURCE-reported `occurredAt` (never the completion time, so delayed jobs keep correct event chronology) — and normalizes candidates with exact Phase 8 mapper parity (dedupe by uppercased SKU keeping the strongest, sort by confidence descending, 1-based ranks, scores rounded to 4 decimals, cap 20; record-only event types may complete with zero detections, basket-affecting types require at least one) into an **append-only** `InferenceResult` + `InferenceCandidate` rows (DB triggers; what an adapter produced never changes). Adapters receive the claimed job's context (id, tenant, job type, screened descriptor) on every call, so a real provider plugs in behind the contract without out-of-band lookups. `POST /inference/jobs/:id/to-vision-event` (permission `inference:apply`; re-checks the `cv` module inside the flow so a cv-disabled tenant has no back door) converts a SUCCEEDED result into a Phase 7 vision event through the EXISTING `VisionEventsService.ingest` contract — type from the suggestion, `quantity = |quantityDelta|` (negative deltas only for `PRODUCT_RETURN`, DB-enforced), the ranked candidates, and a deterministic `inference:<jobId>` idempotency key, so conversion is one-shot and replay-safe; the `inference:` namespace is RESERVED (public vision ingest rejects it) and a replayed event is verified against the job's result before linking, so a squatted key can never bind a foreign event to a job; the event lands in `PENDING_REVIEW` and the basket changes only on an approved review. Every mutation is audited with before/after snapshots; composite same-tenant FKs backstop tenant isolation. **No real model executes in Phase 9** — no NVIDIA/DeepStream/Triton/GStreamer/FFmpeg/Celery/Redis/PyTorch/OpenCV or any ML/video/broker runtime dependency was added; vendors may appear in docs as future adapters only (pinned by a vendor-neutrality test).

- **Video ingestion & crop extraction (Phase 10)** — the first controlled on-ramp for REAL test footage into the Phase 9 pipeline, with NO production camera runtime and NO real model execution. `POST /video-assets` (permission `video-asset:manage`, module `video-ingest`) accepts a multipart upload of a short controlled test clip with layered safety: container allowlist (mp4/m4v/mov/webm/mkv/avi/mpg/mpeg — extension + declared MIME + magic bytes must all agree, so a script renamed `.mp4` is a controlled 400), a conservative configurable size ceiling (`VIDEO_MAX_UPLOAD_BYTES`, default 50 MiB, enforced at the multipart layer AND re-checked in the service), traversal-shaped filename REJECTION (separators, `..`, drive colons, hidden names, control characters) plus display-only sanitation, and credential-/payment-bearing filename screening. The row stores metadata + a SHA-256 checksum + an INTERNAL server-generated storage key (`tenant/randomUUID/original.ext` — the client filename never participates); **raw media never enters the database, no public or signed URLs exist, and the storage key is excluded from every API response and audit snapshot at the SELECT layer**. Staging is **DB-first**: the asset row (with key/size/checksum — all known from the in-memory buffer) commits BEFORE any byte reaches storage in the NON-SCREENABLE `PENDING_MEDIA` state, so **the row is the recovery record for orphaned media** — a crash between the row commit and the media write can never strand bytes that nothing references (the old put-then-create ordering could) — and the asset is published `PENDING_MEDIA → QUARANTINED` (audited CAS) only AFTER the media write succeeds, so a screener can never APPROVE an asset whose bytes might still fail to land; a media write that fails after the commit removes the media directory best-effort and transitions the row `PENDING_MEDIA → FAILED` with a stable `UPLOAD_INCOMPLETE` code (audited, surfaced as the existing controlled 503), a PENDING_MEDIA row left by a crash degrades controlled everywhere (screening decisions, the screening preview, validate, and extraction all 409 on it; DELETE cleans the row), and hierarchy-validation rejections now happen before any bytes are written at all. A concurrent `DELETE` racing an in-flight upload is handled honestly on BOTH sides of the media write: an advisory-lock-guarded liveness re-check immediately before the put (same per-asset lock as the soft-delete, never held across file I/O) skips the write with a controlled 409 when the delete already committed — shrinking the window in which fresh media could land AFTER the delete's cleanup ran — and when the publish CAS still loses, the compensating media removal is retried once and, if it keeps failing, is NEVER swallowed: the caller gets a retryable 503 naming the orphaned-media condition and an audit entry records the durable cleanup obligation, which the idempotent `DELETE /video-assets/:id` replay discharges by re-running the same prefix removal. Bytes live under a gitignored local/dev root behind a `VideoStoragePort` (root-confined keys — traversal/absolute/unsafe-charset keys throw before any filesystem call; object storage arrives later behind the same port). `POST /video-assets/:id/validate` (permission `video-asset:process`) probes real duration/dimensions/fps through a `VideoFrameExtractorPort` — the deterministic SIMULATED extractor by default (dev/test/CI need no media tooling), or an OPTIONAL local ffmpeg/ffprobe system-binary adapter behind `VIDEO_FFMPEG_ENABLED=true` (argument vectors only, integer-validated, no shell, controlled errors that never echo stderr/paths; never an npm dependency — pinned by the module's vendor-neutrality test). `POST /video-assets/:id/extract-frames` and `POST /video-assets/:id/crops` create append-only `VideoArtifact` rows (FRAME/CROP; DB trigger allows exactly ONE later mutation — the one-shot inference-job link) with timestamps validated STRICTLY inside the probed duration and crop boxes inside the probed dimensions; crop reasons are a CLOSED vocabulary (no free text). Both endpoints take an optional tenant-scoped `idempotencyKey`: the committed batch (artifact rows + audits + the READY flip + an append-only `VideoExtractionRequest` record) publishes in ONE transaction, and a retried or concurrent identical request REPLAYS the recorded artifacts — append-only rows are never duplicated, and a key can never replay across a different asset or operation type. Artifact files are staged under **DETERMINISTIC keys** — `<assetPrefix>/artifacts/<sha256 of the request identity>/<index>.png`, the identity being the idempotency key when supplied, else the canonical request fingerprint — and the committed rows record those staged keys DIRECTLY (no rename/promotion step, which would just reintroduce a put/commit crash window), so a crash between the staged writes and the batch commit is **self-healing**: a replayed identical request re-puts over the SAME keys (the storage adapter publishes atomically via temp-file + rename, so overwrite is safe) instead of orphaning fresh UUID files nothing references, a changed-parameters same-key retry is the usual fingerprint-guard 409 with no new writes (leftovers from a crashed attempt stay discoverable under the asset's `artifacts/<sha256>/` operation prefix — the staged namespace is reconcilable by key shape alone, deliberately with NO scavenger job, and asset deletion's recursive prefix removal cleans it with everything else), and the failure-path cleanup consults the committed artifact rows first so it never deletes a staged key an earlier committed batch recorded (deterministic keys are shared across identical attempts; when that ownership check itself cannot run the cleanup fails closed — 503, files kept — because keeping deterministic staged files is always recoverable and deleting blindly is not). Because those keys are SHARED by identical attempts, the whole staging → publication → cleanup section runs under an advisory lock keyed on the OPERATION (tenant + asset + the very hash the staging keys are derived from): without it a failing attempt could run its committed-owner lookup while the winning attempt's artifact transaction was still uncommitted, see no owner, and delete the shared file out from under the winner's append-only rows. Serialized, the loser always reaches its cleanup AFTER the winner committed, finds the winner's batch through the in-transaction replay path, and keeps the files (the committed-owner check stays as defense in depth). The lock is a `pg_advisory_xact_lock` held by ONE interactive transaction whose only job is to hold it — deliberately not the session-level `pg_advisory_lock`/`pg_advisory_unlock` pair, whose unlock can land on a different pooled connection and leak the lock forever; a transaction-scoped lock is released on commit, rollback, timeout, and process death alike. Contention past the configured hold ceiling surfaces as a retryable 503, never an uncontrolled 500. Upload screening also covers the PAYLOAD: printable text in container metadata (ASCII and UTF-16 — MP4 ilst/ID3 atoms) is screened with a single fused free-text predicate (`containsSensitiveFreeText`) covering credential fragments (down to `cvv=…`-length runs), bare well-known secret tokens, credential labels FUSED with their value in one token (`cvv123`, `pin1234`), and payment-card numbers under a **Luhn-verdict-wins** PAN policy: EVERY 13–19-digit window inside any contiguous digit run, and every window of separator-joined digit groups (whatever the grouping or separator), is Luhn-tested with NO shape/context exemptions — a Luhn-valid camera-timestamp or GPS digit join rejecting is accepted overbreadth (operators rename the file or strip the metadata), because every exemption is a laundering channel. The SAME predicate screens every persisted operator free-text field (screening notes, idempotency keys, filenames), so a fused `cvv123` note is a controlled 400 before any read or transition. Frame-VISIBLE content cannot be screened by text checks, and an operator attestation proves nothing about the bytes — so uploads are FRAME-SCREENED BEFORE STORAGE, entirely from the IN-MEMORY buffer (the unscreened bytes never touch any disk — the buffer-inspection session is in-memory only, so a crash mid-screen retains nothing under `VIDEO_STORAGE_ROOT`; EVERY decoded source frame — the complete frame stream, no fps filter and no sampling of any kind (an fps=1 sample would let content visible only between one-second ticks reach storage unscreened) — is decoded in one exhaustive pass and OCR-screened with the same fused predicate (byte-identical frames are sha256-deduped before OCR, so static scenes collapse without weakening the screen, and a hit is still attributed to the first frame index carrying those bytes), with clips whose probed duration exceeds the configurable `VIDEO_MAX_SCREENING_DURATION_MS` ceiling (default 30 s) OR whose estimated frame count (ceil(fps × duration)) exceeds the configurable `VIDEO_MAX_SCREENING_FRAMES` budget (default 900 = 30 fps × 30 s) refused before any decode; a hit, a decode past the frame budget (VFR clips can exceed the estimate), INCOMPLETE frame coverage (fewer decoded frames than started seconds — a sanity floor every real full decode clears; zero included), or a frame over the per-frame screening byte budget is a controlled 400 with the stable `PRESTORE_SCREENING_REJECTED` code and the media never reaches durable storage; uploads are refused 503 when the screen cannot run — there is NO bypass in any environment: `VIDEO_UNSAFE_ALLOW_UNSCREENED_UPLOADS` is unsupported and fails startup when set — see "Pre-storage frame screening" under Environment variables) and every stored upload STILL lands **QUARANTINED**: the bytes are held in local never-served storage but the asset is NOT processable (validate/extract-frames/crops are controlled 409s) until an audited frame-content screening decision releases it. `POST /video-assets/:id/screening-preview` (same `video-asset:screen` permission) gives the screener a real inspection path before deciding — it is the module's **only byte-exposing surface**: up to 6 sample frames — one per started second, evenly spread once the cap bites (the preview stays a bounded SAMPLE; the pre-storage screen is the surface that inspects every source frame) — are extracted IN MEMORY through the extractor port and returned base64-encoded with timestamps, available **only while the asset is QUARANTINED** (409 otherwise), **audited on every serve** (`READ` audit action with the frame count), with frames **never persisted** (no artifact rows, no storage writes, and a preview-specific decoded-byte cap of 16 MiB per response — much tighter than the extraction batch budget because the bytes return base64-inflated in one JSON body; the remaining allowance bounds every extractor call BEFORE the decode, and over-budget frames are skipped and reported) and the video container / **original bytes never downloadable**. The preview **requires the byte-reading extractor** (`VIDEO_FFMPEG_ENABLED=true`): the default simulated extractor renders deterministic placeholder pixels that ignore the stored media, so under it the preview is a controlled 503 and no frames are served — simulated mode can still REJECT (safe direction), but APPROVE without a real inspection is exactly the blind attestation the preview exists to eliminate, so **any deployment that screens real uploads — production above all — must run the real extractor**; extractor trouble is a retryable 503 and unreadable content a controlled 400 with NO status transition (a preview failure never auto-rejects — the screening decision stays open). `POST /video-assets/:id/screening` (permission `video-asset:screen`, its own least-privilege duty) records that decision: `APPROVE` transitions QUARANTINED → UPLOADED through the same audited CAS machinery as every other transition; `REJECT` first claims the terminal transition QUARANTINED → REJECTED with a stable `SCREENING_REJECTED` error code (the claim's message and audit record the media removal as PENDING — never as done before it happened) and then removes the stored media (retry-once/escalate-503 cleanup; replaying the rejection completes an interrupted removal), writing a separate completion audit entry only once the removal actually succeeded — the metadata row is kept as evidence. Quarantine is a LIFECYCLE STATE enforced at every processing entry point, not a storage directory — files never move, so no new orphan classes exist. The required upload attestation (`attestNoSensitiveContent=true`) remains as audited defense-in-depth on top of the quarantine gate, and the Phase 11 automated CV frame screener plugs into this same screening step behind the same gate. The optional binary extractor probes display geometry (rotation side-data honored), prefers `avg_frame_rate` for VFR sources, and treats end-of-stream during sampling as a normal stop — an explicit timestamp past the last decodable frame is a controlled 400, never a FAILED asset. `POST /video-crops/:id/inference-job` (permission `video-asset:process`; re-checks the `inference` module inside the flow) creates a Phase 9 job through the EXISTING `InferenceJobsService.create` contract with a SAFE descriptor referencing the artifact BY OPAQUE ID only (screened again by the Phase 9 media policy) and a derived `video-crop:<artifactId>` idempotency key — retries and races replay the same job; the artifact's job link is stamped once via compare-and-set. Every replay is verified against the full server-derived job identity — the complete descriptor, the asset's context bindings, the resolved jobType, the resolved priority (`priority` when supplied, else the inference module's default — so a retry asking for different queue ordering is a 409, never reported as a successful replay of the original job), AND the `VISION` sourceType the creation stamps explicitly (never left to a schema default, never client-tunable) — so a same-tenant caller who pre-created the derived key with a matching descriptor but ADMIN/MANUAL provenance cannot get the crop linked to it and hand its eventual VisionEvent false provenance: preclaimed and already-linked replays alike are a controlled 409 with no link. `DELETE /video-assets/:id` (permission `video-asset:delete`) commits the DURABLE, AUDITED soft-delete first, then retires inference jobs already linked through the asset's crop artifacts (QUEUED jobs are cancelled through the audited inference seam; a job already claimed is recorded as an orphan condition — deleted media never leaves claimable queue work behind), and only then removes the LOCAL files (original + artifacts); the endpoint is idempotent over already-deleted assets, so an interrupted file cleanup is completed by retrying — filesystem removal can never precede the audited transition. The soft-delete (which takes the same per-asset advisory lock as the screening decisions, the preview's final serve authorization, AND the crop→job link — so a preview can never be audited/served after a deletion committed, and a crop link can never commit after the delete flow enumerated the jobs to retire) records the media cleanup as PENDING; a separate completion audit entry lands only after the job retirement and storage removal actually succeeded, recorded EXACTLY ONCE through a DB `mediaRemovedAt` marker compare-and-set shared with the screening-rejection removal (the marker — never the filesystem's "did anything exist" report — decides, so concurrent replays cannot duplicate the completion evidence and a replay can repair a completion record whose audit write failed). When a screening rejection already removed the media and recorded that completion, a later DELETE is audited honestly as a METADATA-ONLY deletion (the earlier completion entry is the removal evidence; no second completion is promised or attempted) — the marker is read inside the soft-delete's locked transaction, so the wording can never race the screening removal. **Deleting a STAGED upload (`PENDING_MEDIA`) is deliberately left INCOMPLETE**: that row's durable media write is still undecided, so an in-flight upload whose liveness check passed before the soft-delete committed can land bytes moments after the cleanup ran — stamping the exactly-once completion marker there would record a cleanup as finished over a prefix the bytes had not yet reached, and no later replay could ever record the real one. So the removal runs, the marker is left UNSET, and the delete audit says so explicitly ("staged upload may still land bytes"). The soft-deleted row — which already records the storage key — IS the drain marker, and because `DELETE /video-assets/:id` stays idempotently repeatable over an already-deleted asset, **a crashed staged upload is drained by replaying DELETE**: the replay re-runs the prefix removal (removing anything that landed in the window) and only then records the completion, exactly once. The unset marker is what makes that outstanding obligation non-silent — a completed staged delete and a pending one are distinguishable in the durable state, so reconciliation (or an operator) can find and finish it. The metadata row is kept for audit lineage; deleted assets 404 on every ordinary read. Tenant isolation is backstopped by composite same-tenant FKs on every reference; every mutation is audited. **No GStreamer/DeepStream/Triton, no broker queues, no VLM, no cloud media storage, and no committed media** — uploads/frames/crops live only under the gitignored storage root.

## Environment variables

See [.env.example](.env.example). `DATABASE_URL` and `JWT_SECRET` are required; `PORT` (default 3000), `CORS_ORIGINS` (default `http://localhost:5173`, the admin web dev server), and `NODE_ENV` are optional. Never commit a real `.env`.

Phase 10 (all optional): `VIDEO_STORAGE_ROOT` (local/dev media root, default `<repo>/.local/video-ingest`, gitignored — never a public bucket, never exposed through the API), `VIDEO_MAX_UPLOAD_BYTES` (upload ceiling, default 52428800 = 50 MiB), `VIDEO_FFMPEG_ENABLED` (`true` opts in to the local system ffmpeg/ffprobe extraction adapter; default off — the simulated extractor needs no media tooling, but it renders placeholder frames, so the quarantine screening preview refuses to serve under it (controlled 503): informed screening — and any APPROVE decision — requires the real extractor, and production must run with this enabled), `VIDEO_OCR_ENABLED` (`true` opts in to the local system tesseract frame-text recognition adapter used by the PRE-STORAGE frame screen; default off — the simulated recognizer never reads pixels, so with it uploads fail closed), `VIDEO_MAX_SCREENING_DURATION_MS` (ceiling on the probed duration eligible for the mandatory pre-storage frame screen — EVERY decoded source frame of an upload is OCR-screened, so this and the frame budget below together bound the synchronous upload request; default 30000 = 30 s, boot-validated bounds 1000–300000, and a longer clip is a controlled, audited 400 before any byte is stored), `VIDEO_MAX_SCREENING_FRAMES` (ceiling on the DECODED FRAME COUNT eligible for that screen — the exhaustive decode inspects every source frame, so worst case one upload costs up to this many synchronous OCR calls, mitigated by sha256 dedupe of byte-identical frames; default 900 = 30 fps × 30 s, boot-validated bounds 30–3600, and a clip whose estimated frame count ceil(fps × duration) exceeds it — or whose VFR decode still runs past it — is the same controlled, audited 400 with nothing decoded/stored), and `VIDEO_UNSAFE_ALLOW_UNSCREENED_UPLOADS` (**UNSUPPORTED — there is no unscreened-upload bypass in ANY environment**: uploads are never persisted before frame screening, and that invariant has no development/test exception, so startup env validation FAILS with "not supported because raw media cannot be persisted before screening" whenever the flag is `true` — under `development`, `test`, `production`, and an unset `NODE_ENV` alike. The variable remains declared only for compatibility, so existing env files carrying it as `false`/unset still boot; the video-ingest service never reads it). All of these variables are declared in the startup env validation (`validateEnv` whitelists unknown keys, so an undeclared flag would be silently stripped before the modules read it — that is exactly the bug that once made every deployment's uploads 503).

#### Pre-storage frame screening (uploads)

Filename and container-text checks cannot see a PAN that is visible **in the pixels** of an upload, and the operator attestation proves nothing about the bytes — so `POST /video-assets` performs REAL frame screening against the in-memory upload BEFORE any byte reaches durable storage, or refuses the upload when that inspection cannot run. The frame-content defense is LAYERED: (1) the byte-level text screen over the container (metadata/subtitle text), (2) the pre-storage OCR frame screen — the upload is inspected **entirely from the in-memory buffer** through the extraction port's buffer-inspection session: the session is IN-MEMORY ONLY, so unscreened bytes are never written to ANY disk (a non-faststart/unstreamable container that cannot be probed from memory FAILS CLOSED as a `PROBE_FAILED` rejection with a fixed, controlled message; the `PENDING_MEDIA` row is the only artifact a crash leaves and `DELETE /video-assets/:id` cleans it). The screen is **EXHAUSTIVE — every source frame, no sampling**: an fps=1 sample would drop every frame between one-second ticks, letting a PAN visible only between samples reach storage unscreened. First the probed duration is gated by `VIDEO_MAX_SCREENING_DURATION_MS` (default 30 s) and the probe-estimated frame count (ceil(fps × duration)) by `VIDEO_MAX_SCREENING_FRAMES` (default 900 = 30 fps × 30 s) — a clip past either budget cannot be exhaustively screened inside the synchronous request, so it is an audited `PRESTORE_SCREENING_REJECTED` 400 before any decode; then ONE exhaustive pass (no fps filter) decodes EVERY source frame under a per-frame byte budget and the frame budget (a VFR decode that still runs past the budget is the same audited 400), and each frame's OCR-recognized text runs through the same fused sensitive-text predicate (Luhn-wins PAN windows, credentials, fused labels). **Worst-case request cost**: up to `VIDEO_MAX_SCREENING_FRAMES` (default 900) synchronous OCR calls for one upload — mitigated by sha256 dedupe of byte-identical frames (identical bytes ⇒ identical pixels ⇒ identical verdict, so static test scenes collapse to a handful of recognitions, with a hit still attributed to the FIRST frame index carrying those bytes); the duration and frame budgets together bound the work. A hit transitions the staged row `PENDING_MEDIA → REJECTED` with the stable `PRESTORE_SCREENING_REJECTED` code and a controlled 400 (the recognized text is NEVER echoed, stored, or audited — only the tripping frame's index in the decoded stream); **incomplete frame coverage** — fewer decoded frames than started seconds (a sanity floor: a full decode of any real clip yields at least one frame per second), zero included — FAILS CLOSED the same way with a distinct "incomplete frame coverage" reason (partial coverage is never a pass), as does a frame over the screening byte budget (a frame that cannot be inspected cannot be stored); extractor/recognizer tooling trouble fails the row (`UPLOAD_INCOMPLETE`, retryable 503) — and (3) the quarantine + human screening-preview decision, which remains the human backstop. **Honest limits**: OCR sees machine-readable text only — it can miss stylized/low-contrast fonts, motion blur, and non-text card imagery (a card photographed without legible digits); that is exactly why the quarantine screening decision stays mandatory after the automated screen. When the configured extractor does not read real bytes or the recognizer does not read real pixels (either flag off), uploads are refused with a controlled 503 naming `VIDEO_FFMPEG_ENABLED`/`VIDEO_OCR_ENABLED` BEFORE any row or byte is accepted — **there is NO exception**: the former `VIDEO_UNSAFE_ALLOW_UNSCREENED_UPLOADS` bypass is unsupported (setting it `true` fails startup in every environment) because raw media cannot be persisted before screening.

### Recommended Phase 10 test videos

Short, controlled clips work best for exercising the upload → validate → crop → inference-job flow: 10–30 seconds, fixed camera, a known shelf zone, and ONE known expected product action per clip — one product pickup, one product return, a crowded-shelf removal, a false touch with no pickup, and a cart insertion. Never upload real customer footage; these are staged test clips only, and nothing under the local storage root is ever committed.
