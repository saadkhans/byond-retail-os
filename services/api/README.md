# @byond/api — Core Platform API

The BYOND cloud control plane: tenants, users, auth + RBAC (Phase 2), stores/locations, platform modules, the append-only audit log, product catalog + inventory ledger (Phase 3), retail units, devices, and the edge-registration foundation (Phase 4), checkout sessions + orders (Phase 5), the provider-neutral payment abstraction + reconciliation foundation (Phase 6), CV product recognition + virtual basket (Phase 7), the CV inference adapter + event queue foundation (Phase 9), and the video ingestion + crop extraction MVP (Phase 10). NestJS 11 + TypeScript strict + Prisma + PostgreSQL.

### Phase 6 — payments & reconciliation (foundation only)

Phase 6 introduces a **provider-neutral** payment abstraction. It deliberately does **not** integrate a live payment gateway:

- **No live gateway / no provider SDK.** There is no MyFatoorah/Stripe/Tap/HyperPay/Moyasar (or any) SDK. `provider` is a generic enum (`SIMULATED`/`MANUAL`); real gateway adapters plug in through this abstraction later.
- **Authorization and capture are SIMULATED** through an explicit payment state machine (`CREATED → REQUIRES_AUTHORIZATION → AUTHORIZED → CAPTURE_PENDING → CAPTURED`, plus `FAILED`/`CANCELLED`/`VOIDED`/`EXPIRED`). Invalid transitions are rejected, terminal states are protected, and every mutation is audited.
- **No raw card data or secrets, ever.** Only opaque provider references and **safe** card metadata are stored — `instrumentBrand`, `instrumentLast4` (exactly four digits, DB-enforced), `instrumentExpiryMonth/Year`, `instrumentWallet`. Raw PAN, CVV, PIN, magnetic-track data, provider secret keys, bearer tokens, API keys, and raw webhook secrets/payloads are **never** accepted, stored, logged, or audited (screened by `common/sensitive-keys`).
- **Order is not "paid" unless the payment reaches CAPTURED.** A captured intent is the only path that flips a linked order's `paymentStatus` to `PAID`; a failure/void never marks an order paid, and a `PAID` order is never downgraded. Refunds are reserved (`REFUND_PENDING`/`REFUNDED`) but **not** implemented — no money movement.
- **Idempotency & duplicate-capture safety.** Create/authorize/capture carry tenant-scoped idempotency keys; a duplicate capture with the same key **never** moves money twice. Provider events are deduplicated per `(tenant, provider, providerEventId)`.
- **Provider events are an ingestion FOUNDATION** — authenticated/admin-only (`POST /payment-events/simulate`), **not** a public webhook. Only normalized fields are stored (no raw payload, no signature verification yet).
- **Reconciliation is a FOUNDATION** — a `PENDING` record is seeded on capture, with read models and a manual status update. No settlement accounting, provider import, or Zoho integration.

## Architecture notes

- **Tenant isolation** — every tenant-scoped repository extends [`TenantScopedRepository`](src/prisma/tenant-scoped.repository.ts): all methods take `tenantId` first and merge it into every query; a blank tenantId throws, never wildcards. Platform-scoped repositories (Tenant, Permission, PlatformModule) are explicitly documented as such.
- **Platform vs tenant users** — single `User` table with a `userType` discriminator; a DB CHECK constraint enforces `PLATFORM ⇔ tenantId IS NULL`.
- **Audit log** — append-only: no update/delete service methods, a DB trigger rejects `UPDATE`/`DELETE`, and before/after snapshots pass a redaction filter.
- **Catalogs as code** — permissions ([permission.catalog.ts](src/access-control/permission.catalog.ts)) and platform modules ([platform-module.catalog.ts](src/platform-modules/platform-module.catalog.ts)) are typed constants; the seed upserts from them, so codes never drift.
- **Auth** — Phase 2: bcrypt credentials, short-lived HS256 JWTs, a global auth guard, and a permissions guard that audits every denial. Tenant context comes exclusively from the authenticated user — a `tenantId` in any request body is rejected by the global whitelist `ValidationPipe`.
- **Stores / units / devices (Phase 4)** — the `Location` entity is the store/branch/site concept, served under both `/locations` and `/stores`. `RetailUnit` (smart fridge/shelf/kiosk/... with a DRAFT→ACTIVE→MAINTENANCE/DISABLED→RETIRED lifecycle) belongs to a store; `Device` (camera/lock/sensor/... with per-tenant-unique serials, heartbeats, and `lastSeenAt`) belongs to a unit. Composite same-tenant FKs in migration SQL make cross-tenant references impossible even if an unscoped id slipped through code. Deletion is Restrict-guarded: stores with units/inventory and units with devices return controlled 409s. **Reparenting is likewise guarded since Phase 10**: moving a unit to another store or a device to another unit is a controlled 409 while live (non-deleted) Phase 10 video assets reference it — assets denormalize the store/unit/device hierarchy they were captured under as historical evidence, and reparenting would strand their crops at the inference queue with a stale tuple (unit-location-mismatch / device-unit-mismatch). Delete the referencing assets first (their recorded bindings are the evidence of where the footage was captured); soft-deleted assets never block, and the check runs under the same unit/device advisory locks the upload path holds, so a concurrent upload cannot slip past it.
- **Edge registration (Phase 4)** — `POST /devices/:id/registration-token` (permission `device:register`) issues a one-time token whose **SHA-256 hash alone** is stored; the plaintext is returned once and never logged or audited. The unauthenticated `POST /edge/register` redeems it (serial-bound, single-use, 60-minute expiry; every failure is the same generic 401). Phase 7 will exchange this registration for long-lived edge credentials — none are minted today.
- **Checkout sessions + orders (Phase 5)** — tenant-scoped checkout sessions (`OPEN → ACTIVE → PENDING_REVIEW → COMPLETED/CANCELLED/EXPIRED`) belong to a store and retail unit, carry basket lines with immutable product snapshots (sku/name/UoM/quantity), and complete atomically into a `CONFIRMED` order in a single transaction: per-line `SALE` inventory movements (conditional decrement, `referenceType='Order'`) either all succeed or the whole completion — order included — rolls back. Order numbers are unique per tenant (`ORD-000001`); duplicate completion is prevented by tenant-scoped idempotency keys that replay the original result. **No payment capture exists in Phase 5** — pricing/totals columns are nullable placeholders and no order state means "paid"; payments arrive in a later phase.
- **Vendor-neutral evidence lineage (Phase 5, hardened in Phase 7)** — sessions, basket lines, and order lines carry generic evidence/source reference fields (`sourceType`, `sourceId`, `evidenceBundleId`, `visionEventId`, `vlmReviewId`, `evidenceScore`, `evidenceQuality`, `reasonCodes`). Since Phase 7, `evidenceBundleId`/`visionEventId` are **canonical** references to the Phase 7 `EvidenceBundle`/`VisionEvent` tables: validated tenant-scoped at the data-access layer and backstopped by composite same-tenant FKs, so dangling or cross-tenant CV lineage is impossible. Opaque values stored by the Phase 5 API before those tables existed are preserved verbatim in separate read-only `externalVisionEventRef`/`externalEvidenceBundleRef` columns by the `legacy_vision_ref_compat` migration — they are never resolved against (or promoted to) Phase 7 lineage, and completion copies them onto orders in those same external columns. **Basket-affecting** vision events can never be cited as NEW manual line lineage in any status (controlled 409): pending events would be double-counted when later approved, and decided events already carry their one-shot recorded effect — `POST /vision-events/:id/review` is the only path that applies them to a basket. A patched line may only keep the event reference it already carries (so review-created lines stay manually correctable).
- **CV product recognition + virtual basket (Phase 7)** — the core USP flow: camera/CV event → evidence bundle → SKU candidates → review/policy decision → virtual basket line. `POST /vision-events` (permission `vision:ingest`, module `cv`) ingests normalized product interaction events (`PRODUCT_PICKUP`, `PRODUCT_RETURN`, `PRODUCT_TRANSFER`, `CART_INSERTION`, `EXIT_RECONCILIATION`) with ranked SKU candidates (snapshotted from the tenant catalog), an optional device/session binding, and an optional **lineage-only evidence bundle** (Phase 7 accepts NO evidence payloads: no artifact descriptors, no metadata objects, no URIs/storage keys/hashes, no provenance strings, no inline media in any encoding — the bundle is a lightweight append-only lineage record of `sourceType` + capture window, published as a closed OpenAPI schema with `additionalProperties: false`; every removed payload field is a controlled 400, and external media references arrive in a future evidence storage phase). Ingestion never touches the basket or inventory; events land in `PENDING_REVIEW`. `POST /vision-events/:id/review` (permission `vision:review`) records exactly one terminal decision per event — APPROVE applies the top candidate, OVERRIDE applies the reviewer's product/quantity, REJECT records only — and the decision, the event status flip, the basket line add/increment (pickup, cart insertion) or decrement/soft-remove (return), and every audit row commit or roll back as **one transaction** under the same session/product advisory locks as checkout. `EvidenceBundle`, `VisionEventCandidate`, and `VisionEventReview` are append-only (DB triggers) — evidence and decisions are tamper-evident. Provider neutrality is structural: `sourceType` is a closed enum, reason codes are lowercase slugs, and the user-supplied provenance strings of earlier drafts (`sourceId`/`modelName`/`modelVersion`) are removed — those columns are server-controlled and always null in Phase 7. Remaining free strings (idempotency keys, candidate labels, review reasons) are screened against credential-/payment-bearing content before persistence. No camera integration, edge runtime, or training pipeline exists in this phase.

- **CV inference adapter & event queue (Phase 9)** — the provider-neutral seam between model output and the Phase 7 vision flow, following the event-driven CV architecture (continuous lightweight tracking on DOWNSCALED streams → trigger layer → heavy inference on high-resolution triggered crops only; a VLM only ever verifies cropped product patches). `POST /inference/jobs` (permission `inference:manage`, module `inference`) queues a provider-neutral `InferenceJob` (`TRACKING_EVENT`, `SHELF_AUDIT`, `PRODUCT_RECOGNITION`, `OCR_REVIEW`, `VLM_REVIEW`, `EXIT_RECONCILIATION`; `QUEUED → RUNNING → SUCCEEDED/FAILED`, `CANCELLED` reserved) with an optional store/unit/device/session binding, a 0–1000 priority, a tenant-scoped idempotency key (replays, never duplicates), and a **SAFE input descriptor**: crops/zones/frames are referenced BY ID only — raw media, media/storage URLs, signed URLs, artifact descriptors, inline base64, and credential-/payment-bearing content are all controlled 400s, screened by KEY and by VALUE (URI schemes, media file extensions, presigned-URL signature params). The job table IS the queue (deterministic claim ordering: priority DESC, requestedAt ASC, id ASC; race-safe compare-and-set transitions; lease-based claims — every claim takes a bounded lease and increments an attempt counter, and expired leases from crashed workers are reclaimed on the next claim pass: requeued while attempts remain, `LEASE_EXPIRED`-failed once the budget is spent, each reclaim audited as a system action; `POST /inference/jobs/reclaim-expired` (permission `inference:manage`) triggers the same sweep explicitly so an operator can recover a stranded job without waiting for an unrelated start, and `complete`/`fail` carry the caller-observed claim `attempt` so a stale worker's report is fenced out with a 409 after a reclaim) behind an `InferenceQueuePort` abstraction — message-broker adapters (Redis/NATS/MQTT/Kafka-style) can implement the same port later; none is a dependency today. Adapters implement a provider-neutral `InferenceAdapter` contract (`validateInput`/`run`/`normalizeResult`); Phase 9 registers exactly one, the **simulated** adapter — `POST /inference/jobs/:id/complete` (permission `inference:simulate`) takes sample model output — including the required SOURCE-reported `occurredAt` (never the completion time, so delayed jobs keep correct event chronology) — and normalizes candidates with exact Phase 8 mapper parity (dedupe by uppercased SKU keeping the strongest, sort by confidence descending, 1-based ranks, scores rounded to 4 decimals, cap 20; record-only event types may complete with zero detections, basket-affecting types require at least one) into an **append-only** `InferenceResult` + `InferenceCandidate` rows (DB triggers; what an adapter produced never changes). Adapters receive the claimed job's context (id, tenant, job type, screened descriptor) on every call, so a real provider plugs in behind the contract without out-of-band lookups. `POST /inference/jobs/:id/to-vision-event` (permission `inference:apply`; re-checks the `cv` module inside the flow so a cv-disabled tenant has no back door) converts a SUCCEEDED result into a Phase 7 vision event through the EXISTING `VisionEventsService.ingest` contract — type from the suggestion, `quantity = |quantityDelta|` (negative deltas only for `PRODUCT_RETURN`, DB-enforced), the ranked candidates, and a deterministic `inference:<jobId>` idempotency key, so conversion is one-shot and replay-safe; the `inference:` namespace is RESERVED (public vision ingest rejects it) and a replayed event is verified against the job's result before linking, so a squatted key can never bind a foreign event to a job; the event lands in `PENDING_REVIEW` and the basket changes only on an approved review. Every mutation is audited with before/after snapshots; composite same-tenant FKs backstop tenant isolation. **No real model executes in Phase 9** — no NVIDIA/DeepStream/Triton/GStreamer/FFmpeg/Celery/Redis/PyTorch/OpenCV or any ML/video/broker runtime dependency was added; vendors may appear in docs as future adapters only (pinned by a vendor-neutrality test).

- **Video ingestion & crop extraction (Phase 10)** — the first controlled on-ramp for REAL test footage into the Phase 9 pipeline, with NO production camera runtime and NO real model execution. `POST /video-assets` (permission `video-asset:manage`, module `video-ingest`) is **DISABLED BY DEFAULT** and ingests **CONTROLLED INTERNAL TEST MEDIA ONLY**: the endpoint refuses every upload with a controlled 503 unless `VIDEO_TEST_MEDIA_INGEST_ENABLED=true` **and** `NODE_ENV` is explicitly `development` or `test` (startup validation refuses the flag anywhere else — production and an unset `NODE_ENV` alike — and the service re-checks `NODE_ENV` itself as defense in depth). That **policy gate**, together with four REQUIRED operator attestations (`controlledTestMedia`, `noPaymentCardsVisible`, `noCustomerPII`, `attestNoSensitiveContent`, each the literal `"true"`; any missing/other value is a controlled 400 before any row or byte), is what **authorizes** storing a clip — **no screening result ever does**. With the gate open the endpoint accepts a multipart upload of a short controlled test clip with layered safety: container allowlist (mp4/m4v/mov/webm/mkv/avi/mpg/mpeg — extension + declared MIME + magic bytes must all agree, so a script renamed `.mp4` is a controlled 400), a conservative configurable size ceiling (`VIDEO_MAX_UPLOAD_BYTES`, default 50 MiB, enforced at the multipart layer AND re-checked in the service), traversal-shaped filename REJECTION (separators, `..`, drive colons, hidden names, control characters) plus display-only sanitation, and credential-/payment-bearing filename screening. The row stores metadata + a SHA-256 checksum + an INTERNAL server-generated storage key (`tenant/randomUUID/original.ext` — the client filename never participates); **raw media never enters the database, no public or signed URLs exist, and the storage key is excluded from every API response and audit snapshot at the SELECT layer**. Staging is **DB-first**: the asset row (with key/size/checksum — all known from the in-memory buffer) commits BEFORE any byte reaches storage in the NON-SCREENABLE `PENDING_MEDIA` state, so **the row is the recovery record for orphaned media** — a crash between the row commit and the media write can never strand bytes that nothing references (the old put-then-create ordering could) — and the asset is published `PENDING_MEDIA → QUARANTINED` (audited CAS) only AFTER the media write succeeds, so a screener can never APPROVE an asset whose bytes might still fail to land; a media write that fails after the commit removes the media directory best-effort and transitions the row `PENDING_MEDIA → FAILED` with a stable `UPLOAD_INCOMPLETE` code (audited, surfaced as the existing controlled 503), a PENDING_MEDIA row left by a crash degrades controlled everywhere (screening decisions, the screening preview, validate, and extraction all 409 on it; DELETE cleans the row), and hierarchy-validation rejections now happen before any bytes are written at all. A concurrent `DELETE` racing an in-flight upload is handled honestly on BOTH sides of the media write: an advisory-lock-guarded step immediately before the put (same per-asset lock as the soft-delete, never held across file I/O) both re-checks liveness — skipping the write with a controlled 409 when the delete already committed, which shrinks the window in which fresh media could land AFTER the delete's cleanup ran — and CLAIMS the media write durably (`mediaWriteState = PENDING`) in the same transaction, so a concurrent delete either observes the claim or committed first; the claim is resolved `SUCCEEDED` the moment the put returns (before the publish CAS, which can lose) or `FAILED` when it throws, and when the publish CAS still loses, the compensating media removal is retried once and, if it keeps failing, is NEVER swallowed: the caller gets a retryable 503 naming the orphaned-media condition and an audit entry records the durable cleanup obligation, which the idempotent `DELETE /video-assets/:id` replay discharges by re-running the same prefix removal. Bytes live under a gitignored local/dev root behind a `VideoStoragePort` (root-confined keys — traversal/absolute/unsafe-charset keys throw before any filesystem call; object storage arrives later behind the same port). `POST /video-assets/:id/validate` (permission `video-asset:process`) probes real duration/dimensions/fps through a `VideoFrameExtractorPort` — the deterministic SIMULATED extractor by default (dev/test/CI need no media tooling), or an OPTIONAL local ffmpeg/ffprobe system-binary adapter behind `VIDEO_FFMPEG_ENABLED=true` (argument vectors only, integer-validated, no shell, controlled errors that never echo stderr/paths; never an npm dependency — pinned by the module's vendor-neutrality test). `POST /video-assets/:id/extract-frames` and `POST /video-assets/:id/crops` create append-only `VideoArtifact` rows (FRAME/CROP; DB trigger allows exactly ONE later mutation — the one-shot inference-job link) with timestamps validated STRICTLY inside the probed duration and crop boxes inside the probed dimensions; crop reasons are a CLOSED vocabulary (no free text). Both endpoints REQUIRE a tenant-scoped `idempotencyKey` (a controlled 400 without one, before anything is read, extracted, or staged — and the key is still screened for control characters and credential-/payment-bearing content like every other persisted operator string): the key is the operation's IDENTITY, and the artifact files below are staged under keys derived from it, so a keyless request would let a later identical one rewrite the very file an already-committed append-only artifact row recorded a checksum for — silent lineage corruption the moment the extractor's encoded bytes ever differ (adapter upgrade, any nondeterministic port implementation). With the key present the committed batch (artifact rows + audits + the READY flip + an append-only `VideoExtractionRequest` record) publishes in ONE transaction, and a retried or concurrent identical request REPLAYS the recorded artifacts — append-only rows are never duplicated, and a key can never replay across a different asset or operation type. Artifact files are staged under **DETERMINISTIC keys** — `<assetPrefix>/artifacts/<sha256 of the request identity>/<index>.png`, the identity being the REQUIRED idempotency key together with the canonical request fingerprint (the key is what keeps two different operations off one another's files; the fingerprint is what puts a same-key changed-parameters attempt on a DIFFERENT prefix, so the fingerprint-guard 409 below is decided without either attempt having touched the other's bytes) — and the committed rows record those staged keys DIRECTLY (no rename/promotion step, which would just reintroduce a put/commit crash window), so a crash between the staged writes and the batch commit is **self-healing**: a replayed identical request re-puts over the SAME keys (the storage adapter publishes atomically via temp-file + rename, so overwrite is safe) instead of orphaning fresh UUID files nothing references, a changed-parameters same-key retry is the usual fingerprint-guard 409 with no new writes (leftovers from a crashed attempt stay discoverable under the asset's `artifacts/<sha256>/` operation prefix — the staged namespace is reconcilable by key shape alone, deliberately with NO scavenger job, and asset deletion's recursive prefix removal cleans it with everything else), and the failure-path cleanup never deletes a staged key an earlier committed batch recorded (deterministic keys are shared across identical attempts). Because those keys are SHARED, the PUBLICATION is serialized by an advisory lock keyed on the OPERATION (tenant + asset + the very hash the staging keys are derived from), taken as the FIRST statement of the batch transaction itself: without it a failing attempt could run its committed-owner lookup while the winning attempt's artifact transaction was still uncommitted, see no owner, and delete the shared file out from under the winner's append-only rows. That lookup now runs INSIDE the locked publish transaction and its verdict is returned with the outcome, so it can never observe a rival batch mid-commit, it costs no extra query, and — crucially — **no transaction is ever open across the staging file writes and no locked callback ever needs a second pooled connection** (an outer lock transaction wrapped around the whole section pinned one connection while every call inside it needed another, so pool-sized concurrency could exhaust the pool). Staging itself needs no serialization: identical attempts write identical bytes to identical keys and the adapter's put publishes atomically via temp-file + rename. Deleting a staged file is authorized ONLY on the one outcome that is TERMINAL for the operation — a replay, which requires an idempotency key that is now CONSUMED — an invariant the required key makes unconditional rather than incidental — so no present or future attempt can publish those keys again; every other outcome (the publish threw, the status CAS was lost, the key belongs to another asset, a staging put failed part-way) **fails closed with the files kept**, because a rival attempt may still publish them and keeping deterministic staged files is always recoverable (an identical retry overwrites them, asset deletion removes the whole prefix, and they stay reconcilable by key shape) while deleting blindly is not. The lock is a `pg_advisory_xact_lock`, deliberately not the session-level `pg_advisory_lock`/`pg_advisory_unlock` pair, whose unlock can land on a different pooled connection and leak the lock forever; a transaction-scoped lock is released on commit, rollback, timeout, and process death alike. Contention past the configured wait/hold ceilings surfaces as a retryable 503, never an uncontrolled 500. Upload screening also covers the PAYLOAD: printable text in container metadata (ASCII and UTF-16 — MP4 ilst/ID3 atoms) is screened with a single fused free-text predicate (`containsSensitiveFreeText`) covering credential fragments (down to `cvv=…`-length runs), bare well-known secret tokens, credential labels FUSED with their value in one token (`cvv123`, `pin1234`), and payment-card numbers under a **Luhn-verdict-wins** PAN policy: EVERY 13–19-digit window inside any contiguous digit run, and every window of separator-joined digit groups (whatever the grouping or separator), is Luhn-tested with NO shape/context exemptions — a Luhn-valid camera-timestamp or GPS digit join rejecting is accepted overbreadth (operators rename the file or strip the metadata), because every exemption is a laundering channel. The SAME predicate screens every persisted operator free-text field (screening notes, idempotency keys, filenames), so a fused `cvv123` note is a controlled 400 before any read or transition. Frame-VISIBLE content cannot be screened by text checks, and neither an operator attestation nor an OCR pass proves anything about the bytes — so uploads are additionally TEXT-SCREENED OVER THEIR FRAMES BEFORE STORAGE, as a **rejection layer on top of the policy gate**, entirely from the IN-MEMORY buffer (the unscreened bytes never touch any disk — the buffer-inspection session is in-memory only, so a crash mid-screen retains nothing under `VIDEO_STORAGE_ROOT`; EVERY decoded source frame — the complete frame stream, no fps filter and no sampling of any kind (an fps=1 sample would let content visible only between one-second ticks reach storage unlooked-at) — is streamed one frame at a time (peak memory O(one frame)) and OCR-screened with the same fused predicate (byte-identical frames are sha256-deduped before OCR, so static scenes collapse without weakening the screen, and a DETECTION is still attributed to the first frame index carrying those bytes), with clips whose probed duration exceeds the configurable `VIDEO_MAX_SCREENING_DURATION_MS` ceiling (default 30 s) OR whose estimated frame count (ceil(fps × duration)) exceeds the configurable `VIDEO_MAX_SCREENING_FRAMES` budget (default 900 = 30 fps × 30 s) refused before any decode, and the WHOLE screen — decode plus every recognition — bounded by ONE aggregate wall-clock deadline (`VIDEO_SCREENING_TIMEOUT_MS`, default 30 s) fixed at screening start, re-checked before each recognizer call and handed to the decode, so a slow clip or a wedged binary can never hold the request open; a DETECTION, an expired deadline, a decode past the frame budget (VFR clips can exceed the estimate), INCOMPLETE frame coverage (fewer frames seen than started seconds — a sanity floor every real full decode clears; zero included, and never applied when the stream stopped early on purpose), or a frame over the per-frame screening byte budget is a controlled 400 with the stable `PRESTORE_SCREENING_REJECTED` code and the media never reaches durable storage; uploads are refused 503 when the screen cannot run — there is NO bypass in any environment: `VIDEO_UNSAFE_ALLOW_UNSCREENED_UPLOADS` is unsupported and fails startup when set. **A screen that detects nothing authorizes nothing** — it is an absence of detection, not evidence of absence, and it never substitutes for the policy gate; see "Pre-storage frame screening" under Environment variables) and every stored upload STILL lands **QUARANTINED**: the bytes are held in local never-served storage but the asset is NOT processable (validate/extract-frames/crops are controlled 409s) until an audited frame-content screening decision releases it. `POST /video-assets/:id/screening-preview` (same `video-asset:screen` permission) gives the screener a real inspection path before deciding — it is the module's **only byte-exposing surface**: up to 6 sample frames — one per started second, evenly spread once the cap bites (the preview stays a bounded SAMPLE; the pre-storage screen is the surface that inspects every source frame) — are extracted IN MEMORY through the extractor port and returned base64-encoded with timestamps, available **only while the asset is QUARANTINED** (409 otherwise), **audited on every serve** (`READ` audit action with the frame count), with frames **never persisted** (no artifact rows, no storage writes, and a preview-specific decoded-byte cap of 16 MiB per response — much tighter than the extraction batch budget because the bytes return base64-inflated in one JSON body; the remaining allowance bounds every extractor call BEFORE the decode, and over-budget frames are skipped and reported) and the video container / **original bytes never downloadable**. The preview **requires the byte-reading extractor** (`VIDEO_FFMPEG_ENABLED=true`): the default simulated extractor renders deterministic placeholder pixels that ignore the stored media, so under it the preview is a controlled 503 and no frames are served — simulated mode can still REJECT (safe direction), but APPROVE without a real inspection is exactly the blind attestation the preview exists to eliminate, so **any deployment that screens real uploads — production above all — must run the real extractor**; extractor trouble is a retryable 503 and unreadable content a controlled 400 with NO status transition (a preview failure never auto-rejects — the screening decision stays open). `POST /video-assets/:id/screening` (permission `video-asset:screen`, its own least-privilege duty) records that decision: `APPROVE` transitions QUARANTINED → UPLOADED through the same audited CAS machinery as every other transition; `REJECT` first claims the terminal transition QUARANTINED → REJECTED with a stable `SCREENING_REJECTED` error code (the claim's message and audit record the media removal as PENDING — never as done before it happened) and then removes the stored media (retry-once/escalate-503 cleanup; replaying the rejection completes an interrupted removal), writing a separate completion audit entry only once the removal actually succeeded — the metadata row is kept as evidence. Quarantine is a LIFECYCLE STATE enforced at every processing entry point, not a storage directory — files never move, so no new orphan classes exist. The four required upload attestations (`controlledTestMedia`, `noPaymentCardsVisible`, `noCustomerPII`, `attestNoSensitiveContent`, each `"true"`) are the operator's DECLARATIONS about media they control — audited as the policy the clip was accepted under, never as a finding that the content was inspected and cleared — and the Phase 11 automated CV frame screener plugs into this same screening step behind the same gate. The optional binary extractor probes display geometry (rotation side-data honored), prefers `avg_frame_rate` for VFR sources, and treats end-of-stream during sampling as a normal stop — an explicit timestamp past the last decodable frame is a controlled 400, never a FAILED asset. `POST /video-crops/:id/inference-job` (permission `video-asset:process`; re-checks the `inference` module inside the flow) creates a Phase 9 job through the EXISTING `InferenceJobsService.create` contract with a SAFE descriptor referencing the artifact BY OPAQUE ID only (screened again by the Phase 9 media policy) and a derived `video-crop:<artifactId>` idempotency key — retries and races replay the same job; the artifact's job link is stamped once via compare-and-set. Creation is deliberately **TWO-PHASE and crash-recoverable**: the job is created in the NON-CLAIMABLE `PENDING_LINK` state (an INTERNAL service-only opt-in — no HTTP client can mint one — and the queue claim is pinned to `QUEUED`, so no worker can ever be handed it), the artifact link transaction commits, and only THEN is the job published `PENDING_LINK → QUEUED` through an audited compare-and-set. The old ordering committed a QUEUED job before the link, so a crash in between left claimable work that no later `DELETE` could discover (deletion enumerates jobs reachable through `VideoArtifact.inferenceJobId` — precisely the link that never committed) and no retry could repair (the artifact 404s once its asset is deleted). Now that window leaves nothing claimable and nothing unreachable: the publish CAS is idempotent (a retry whose link committed but whose publish did not finishes the interrupted second phase and returns the QUEUED job — a replayed crop is never reported as successfully linked while its job is still unclaimable; an already-published job answers `not-pending` and is a controlled no-op, never an error), every branch that can never link retires the `PENDING_LINK` row it created instead of publishing it (a job that came back as a REPLAY of somebody else's pre-existing row is left untouched — withdrawing live queue work this flow does not own is never its business), and the DELETE flow below finds the crash-window job by its deterministic key. Every replay is verified against the full server-derived job identity — the complete descriptor, the asset's context bindings, the resolved jobType, the resolved priority (`priority` when supplied, else the inference module's default — so a retry asking for different queue ordering is a 409, never reported as a successful replay of the original job), AND the `VISION` sourceType the creation stamps explicitly (never left to a schema default, never client-tunable) — so a same-tenant caller who pre-created the derived key with a matching descriptor but ADMIN/MANUAL provenance cannot get the crop linked to it and hand its eventual VisionEvent false provenance: preclaimed and already-linked replays alike are a controlled 409 with no link. `DELETE /video-assets/:id` (permission `video-asset:delete`) commits the DURABLE, AUDITED soft-delete first, then retires the asset's inference jobs from TWO discovery sources (jobs already linked through its crop artifacts, PLUS — for every crop that carries no committed link — a lookup under the deterministic `video-crop:<artifactId>` key, which is the only handle on a two-phase job whose link never committed; results are deduped by job id): every job in the inference module's CANCELLABLE set (`PENDING_LINK` or `QUEUED` — work no worker owns yet) is cancelled through the audited inference seam, a job already claimed is recorded as an orphan condition, and terminal jobs are skipped entirely so replays neither re-cancel nor re-audit — deleted media never leaves claimable queue work behind, and the crop→job crash window can no longer hide an unretired job, and only then removes the LOCAL files (original + artifacts); the endpoint is idempotent over already-deleted assets, so an interrupted file cleanup is completed by retrying — filesystem removal can never precede the audited transition. The soft-delete (which takes the same per-asset advisory lock as the screening decisions, the preview's final serve authorization, AND the crop→job link — so a preview can never be audited/served after a deletion committed, and a crop link can never commit after the delete flow enumerated the jobs to retire) records the media cleanup as PENDING; a separate completion audit entry lands only after the job retirement and storage removal actually succeeded, recorded EXACTLY ONCE through a DB `mediaRemovedAt` marker compare-and-set shared with the screening-rejection removal (the marker — never the filesystem's "did anything exist" report — decides, so concurrent replays cannot duplicate the completion evidence and a replay can repair a completion record whose audit write failed). When a screening rejection already removed the media and recorded that completion, a later DELETE is audited honestly as a METADATA-ONLY deletion (the earlier completion entry is the removal evidence; no second completion is promised or attempted) — the marker is read inside the soft-delete's locked transaction, so the wording can never race the screening removal. **A delete whose media write is UNDECIDED is deliberately left INCOMPLETE**: while the asset's durable `mediaWriteState` is `PENDING` an upload has CLAIMED its single storage write (under the same per-asset lock, before the put ran) and has not resolved it, so bytes can land moments after the cleanup ran — stamping the exactly-once completion marker there would record a cleanup as finished over a prefix the bytes had not yet reached, and no later replay could ever record the real one. So the removal runs, the marker is left UNSET, and the delete audit names the outstanding drain obligation. This is a DURABLE OBSERVATION, not an inference: the earlier rule read "the row is `PENDING_MEDIA`" on a fresh delete and treated a REPLAY as proof the write had drained merely because `deletedAt` was already set — wrong for exactly the put that claimed liveness BEFORE the original soft-delete, which is still in flight during that replay. Every attempt now reads the state, so **a crashed or racing staged upload is drained by replaying DELETE**: a replay that still sees `PENDING` withholds the completion again, and the replay that observes the write RESOLVED (`SUCCEEDED`/`FAILED`, or NULL for a row whose put never started) re-runs the prefix removal and only then records the completion, exactly once. The unset marker is what makes that outstanding obligation non-silent — a completed staged delete and a pending one are distinguishable in the durable state, so reconciliation (or an operator) can find and finish it. The metadata row is kept for audit lineage; deleted assets 404 on every ordinary read. Tenant isolation is backstopped by composite same-tenant FKs on every reference; every mutation is audited. **No GStreamer/DeepStream/Triton, no broker queues, no VLM, no cloud media storage, and no committed media** — uploads/frames/crops live only under the gitignored storage root.

This flag is what AUTHORIZES an ingest; it does not make any clip safe, and text/OCR screening never authorizes one), `VIDEO_SCREENING_TIMEOUT_MS` (the AGGREGATE wall-clock budget for screening ONE upload — decode plus every OCR call together, fixed once at screening start, not a per-frame allowance. default off — the simulated recognizer never reads pixels, so with it uploads fail closed), `VIDEO_MAX_SCREENING_DURATION_MS` (ceiling on the probed duration eligible for the mandatory pre-storage frame screen — EVERY decoded source frame of an upload is OCR-screened, so this and the frame budget below together bound the synchronous upload request; #### Controlled test-media ingestion, and what screening does (and does not) prove

**What authorizes an upload is the policy gate, not a screening result.** Phase 10 ingests CONTROLLED INTERNAL TEST CLIPS ONLY, and a clip may be stored only when all of the following hold:

1. `VIDEO_TEST_MEDIA_INGEST_ENABLED=true` **and** `NODE_ENV` is explicitly `development` or `test`. Startup validation refuses the flag in production and under an unset `NODE_ENV`; the service re-checks `NODE_ENV` itself before every upload, so a config that somehow carries `true` in production still ingests nothing. **Uploads are disabled by default** — with the gate shut the endpoint is a controlled 503 that names the flag, before any row, byte, or decode.
2. The caller holds `video-asset:manage` (unchanged — no new permission was invented for this gate).
3. All four operator attestations are present as the literal `"true"`: `controlledTestMedia`, `noPaymentCardsVisible`, `noCustomerPII`, `attestNoSensitiveContent`. They are validated on the DTO and re-checked in the service; anything missing or otherwise valued is a controlled 400 **before any row or byte**. They are DECLARATIONS by an operator about media the operator staged and controls. The audited create entry records exactly that — accepted under the controlled test-media policy with these attestations — and deliberately claims nothing about the content having been inspected or cleared.

**Text/OCR screening is a REJECTION LAYER, and nothing else.** A recognizer that reports no card or credential text has produced an ABSENCE OF DETECTION, not evidence of absence: rotated, blurred, stylized, occluded, small, low-contrast, and low-quality digits defeat Tesseract routinely, and a card photographed without legible digits is not text at all. So a detection REJECTS an upload, and a quiet screen authorizes nothing — the permission came from the gate above. No response, audit entry, error code, or symbol in this module describes a screened clip as clean, card-free, verified, or safe.

With the gate satisfied, the defense is LAYERED: (1) the byte-level text screen over the container (metadata/subtitle text), (2) the pre-storage OCR frame screen described below, and (3) the quarantine + human screening-preview decision, which remains the backstop — every stored upload still lands QUARANTINED and non-processable until an audited screening decision releases it.

**The pre-storage frame screen.** The upload is inspected **entirely from the in-memory buffer** through the extraction port's buffer-inspection session: the session is IN-MEMORY ONLY, so unscreened bytes are never written to ANY disk (a non-faststart/unstreamable container that cannot be probed from memory FAILS CLOSED as a `PROBE_FAILED` rejection with a fixed, controlled message; the `PENDING_MEDIA` row is the only artifact a crash leaves and `DELETE /video-assets/:id` cleans it). The screen is **EXHAUSTIVE — every source frame, no sampling**: an fps=1 sample would drop every frame between one-second ticks, letting a PAN visible only between samples reach storage unlooked-at. Frames are consumed by a **streaming** decode one at a time (peak memory O(one frame) — buffering a whole clip would blow any aggregate memory cap long before the frame budget), and each unique frame's OCR-recognized text runs through the same fused sensitive-text predicate (Luhn-wins PAN windows, credentials, fused labels). Three budgets bound the work, all fail-closed:

- `VIDEO_MAX_SCREENING_DURATION_MS` (default 30 s) gates the probed duration, and `VIDEO_MAX_SCREENING_FRAMES` (default 900 = 30 fps × 30 s) gates the probe-estimated frame count (ceil(fps × duration)) — a clip past either cannot be exhaustively screened inside the synchronous request, so it is an audited `PRESTORE_SCREENING_REJECTED` 400 **before any decode**. A VFR decode that still runs past the frame budget is the same audited 400.
- `VIDEO_SCREENING_TIMEOUT_MS` (default 30 s, clamped to the adapter-enforceable 120 s) is the **AGGREGATE** wall-clock budget for decode AND recognition together, fixed once at screening start as an absolute deadline. Without it the sequential per-frame loop could spend a per-frame recognizer timeout on each of up to `VIDEO_MAX_SCREENING_FRAMES` frames (900 × 30 s ≈ 7.5 hours) on a single request. The remaining budget is handed to the decode as its deadline AND re-checked inside the per-frame callback before every recognizer call, so an expiry abandons the rest of the stream immediately. **An expired deadline is a fail-closed audited rejection** on the same path as the duration and frame budgets (the clip did not fit what this deployment can screen synchronously — nothing about the host is broken), never a pass.
- A per-frame decoded-byte budget: a frame that cannot be inspected cannot be stored, so overrunning it is the same audited 400.

A DETECTION transitions the staged row `PENDING_MEDIA → REJECTED` with the stable `PRESTORE_SCREENING_REJECTED` code and a controlled 400 — the recognized text is NEVER echoed, stored, or audited; only the tripping frame's index in the decoded stream is recorded, and the callback stops the stream gracefully (an early stop is not an error). **Incomplete frame coverage** — fewer frames seen than the clip has started seconds (a sanity floor a full decode of any real clip clears), zero included — FAILS CLOSED the same way with a distinct reason: partial coverage is never treated as a completed screen. The floor is NOT applied when the stream stopped early on purpose (a detection or the deadline), because an early stop legitimately sees fewer frames and already carries its own verdict. Extractor/recognizer tooling trouble fails the row (`UPLOAD_INCOMPLETE`, retryable 503). **Worst-case request cost**: up to `VIDEO_MAX_SCREENING_FRAMES` synchronous OCR calls — mitigated by sha256 dedupe of byte-identical frames (identical bytes ⇒ identical pixels ⇒ identical verdict, so static test scenes collapse to a handful of recognitions, with a detection still attributed to the FIRST frame index carrying those bytes) and hard-bounded by the aggregate deadline.

When the configured extractor does not read real bytes or the recognizer does not read real pixels (either flag off), uploads are refused with a controlled 503 naming `VIDEO_FFMPEG_ENABLED`/`VIDEO_OCR_ENABLED` BEFORE any row or byte is accepted — **there is NO exception**: the former `VIDEO_UNSAFE_ALLOW_UNSCREENED_UPLOADS` bypass is unsupported (setting it `true` fails startup in every environment) because raw media cannot be persisted before screening.

### Recommended Phase 10 test videos

Uploads are accepted only under the controlled test-media policy gate above (`VIDEO_TEST_MEDIA_INGEST_ENABLED=true` with `NODE_ENV` explicitly `development` or `test`), so this flow is a non-production one by construction. Short, controlled clips work best for exercising the upload → validate → crop → inference-job flow: 10–30 seconds, fixed camera, a known shelf zone, and ONE known expected product action per clip — one product pickup, one product return, a crowded-shelf removal, a false touch with no pickup, and a cart insertion. Never upload real customer footage; these are staged test clips only, and nothing under the local storage root is ever committed.
